# Purpose

Measure whether the clarified frozen Manifest, one fixed common shell, and the
same product-facts-only customer-create prompt produce comparable static
customer-create pages across three independent implementations.

This is a `composition-with-fixed-shell` experiment under the
[three-run reproducibility protocol](../../three-run-reproducibility-protocol.md).
It is not a test of manually improving one generated page. The current
Manifest snapshot includes the working-tree clarification prompted by Attempt
9; the baseline commit identifies the prior committed state, not a claim that
the snapshot is committed.

# Consumer-visible input

Each implementation receives exactly these three input directories/files:

1. `consumer-input/design-manifest/` — complete 45-file frozen Manifest snapshot.
2. `consumer-input/common-shell-fixture/` — immutable Header/Drawer shell.
3. `consumer-input/user-prompt-ja.md` — unchanged product-specific customer-create facts.

The prompt deliberately omits generic presentation requirements. The Manifest
owns the form hierarchy, unboxed native fieldset treatment, bounded task-pane
relationship, helper-or-error message region, action treatment, required-marker
treatment, theme tokens, and shell relationship. The prompt owns the customer
labels, field capability, validation facts, and absence of persistence.

# Immutable shell boundary

Copy the fixture's `shell-template.html` to the run's `index.html`, and copy
`shell.css` and `shell.js` byte-for-byte. Insert only the customer-create page
inside `<!-- PAGE_SLOT -->` within `<main class="shell-workspace">`.

Do not alter the Header, Drawer, navigation, theme control, query-state
behavior, shell assets, or markup outside the page slot. Add page-specific
CSS only in `page.css` and page-specific validation only in `page.js`; neither
may restyle shell classes. The fixture supports
`?drawer=open|hidden&theme=light|dark`.

# Evaluation focus

Observe whether every independently generated page:

- omits Customer ID as a control;
- renders the five supplied required fields and optional Notes;
- shows field-associated required, date, telephone, and email validation on
  blur, submission, and correction;
- gives every editable field a one-line reserved helper-or-error region;
- shows muted, completion-critical format help only where it is needed, then
  replaces it with a field-specific error using the shared `error_foreground`
  role without moving the next field for a normal one-line message;
- keeps native fieldset semantics unboxed by resetting browser-default border,
  padding, and margin when a fieldset is used;
- keeps the form as an unboxed bounded task pane and gives its dedicated
  Save/Cancel toolbar logical-start alignment and the default primary-before-
  secondary order;
- keeps Save non-persistent and local-only; and
- preserves the immutable shell across Light/Dark and Drawer states.

No output may be edited or replaced after the three independent runs are
generated. Capture retries are permitted only if the generated bytes stay
unchanged.
