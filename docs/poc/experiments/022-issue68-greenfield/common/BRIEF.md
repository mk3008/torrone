# Document-tab workspace

Build a new Japanese-language document workspace in plain HTML, CSS, and vanilla JavaScript. Browser target is Chromium on Windows. The app starts from the supplied fixture, without prior UI code. The fixture contains documents, their child tabs and initial data configurations. Use the named configuration from ?case= and default to both. Follow the configured counts, then update the layout from actual available space. Keep a focusable workspace action before the rows and a focusable content action after them. Use mock panel content and no persistence.

Show a two-row workspace. Parent tabs switch documents and the child row immediately below belongs to the selected document. Select the first tab of each initially. Put the selection underline at the bottom; use an independent dotted focus indicator inside the focused tab. Use subdued parent group tint and a top edge. Preserve the document order. A close action is centered inside its own tab, with a reserved position. Desktop selected, hovered, or keyboard-focused documents may be closed; on a narrow screen show close on the selected tab. An ellipsized desktop name exposes the full name and affiliation on hover and keyboard focus. Keep the mark secondary to the label and the hit area usable. Use supplied official icon assets directly if using these shapes. Fixture text, colors and typeface are illustrative.

Apply the width rule independently to the two rows. Lay out the normal tabs without auxiliary controls and measure if all fit in that row. When they fit, show all without extra buttons. In desktop mode an overflowing row retains its tabs and has two scroll arrows plus wheel support. Scrolling does not change selection. In narrow mode an overflowing row has one selected tab and a count button, with no scroll arrows. The count button gets its necessary width, and the selected tab uses the rest. Recompute as the screen or shown document changes. In the narrow parent row the right arrow opens a separate document chooser with cards, thumbnails, names and affiliations. The narrow child row uses a down/up chevron and opens an anchored, right-aligned list. Selecting a child updates the content, leaves the document and count stable, and moves the former child into the list.

The target product uses 16px side insets, a narrow layout through 599px, parent tab widths of 140px desktop and 124px narrow, and child tab widths of 112px desktop and 86px narrow. The width is the visible outer surface. Keep a 6px gap between a narrow selected tab and its companion button. These dimensions define the normal layout for this trial. Use the ordinary sizing of the actual row to decide when it overflows. The visible count label is ほかN. The shell can be bounded at a wider width as appropriate.

Use manual activation. Left/Right move keyboard focus among visible tabs without selecting, Enter/Space select, and Tab/Shift+Tab reach neighboring controls. Escape dismisses a chooser and returns to its trigger. Choosing a document focuses its selected tab; choosing a child from the list focuses the trigger. Close the requested tab; preserve the selected document when closing an inactive one. Focus the next remaining document or the previous if at the end. With none remaining, return focus to the workspace action. Keep selected state accessible and include the visible count in each chooser's accessible name.

## Shared browser contract

Provide index.html, app.js and styles.css at the project root. Use data fixtures from fixture.json. Render a .reference container with each composed row as .row, ordered parent then child. Use semantic tablist and tab roles with aria-selected. Use .parent for the outer visible surface of each parent tab. Mark desktop scroll buttons with data-scroll, and use accessible names `文書を左に送る` and `文書を右に送る` for the parent row. Use .more on the narrow count buttons, with the complete visible label as text. Accessible names for document selection should include `文書を切り替える`; the West Japan order card should include the name and region. Use a level-two heading for the content, e.g. `受注管理の概要`. Decorative icons must not add text to count buttons.

Deliver the runnable standalone screen and concise notes on assumptions, what was self-checked, and any gaps. Build or author optional support artifacts as allowed by the workflow. Do not read outside your project or try to find the evaluation suite.
